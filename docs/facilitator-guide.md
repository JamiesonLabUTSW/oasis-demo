# Facilitator guide

Start with [the shared workflow and vocabulary](audience-guide.md), then choose
one session format. Say what participants will actually see before opening an
application or starting a task.

## Choose a teaching format

| Format | Preparation | What it demonstrates |
| --- | --- | --- |
| Manual notes practice | Open the [three fictional notes](../demos/synthetic-notes/README.md); keep answers hidden initially | Finding explicit evidence and applying three original criteria; no installation, model or account |
| Saved-result application tour | A rehearsed host, exact named compatible synthetic sample/rubric/run and verified export | Inspecting model suggestions and source evidence; no new inference required |
| Optional live segment | An explicitly agreed sample/model/provider route, expected cost, time allowance and saved-result fallback | The bounded task actually run; it does not establish general accuracy or participant-machine readiness |
| CDC source discussion | Open the [external recording reference](../demos/cdc-conversation.md) with attribution visible | Discussing observable evidence; no OASIS import/transcription/grading claim |

The public notes rubric is a readable teaching table, not a verified MAPLES
import workbook. Its answers were authored for the exercise. Use the supplied
kit's compatible sample for an application run until this public exercise has
its own import and end-to-end acceptance receipt.

A CDC application segment needs a separately cleared rubric and the host's
rehearsed media/model route. This library supplies no media file, derivative,
transcript or accompanying rubric. Do not treat source-video availability as
permission for an unrelated instrument or as proof of software acceptance.

## Before participants arrive

- Record the chosen format, exact package/platform and named demonstration input.
  Check [current runtime status](runtime.md); image publication alone does not
  qualify a fresh recipient installation.
- Start the rehearsed instance using its own kit. Confirm health, sign-in and
  the named synthetic sample. Keep login helpers off the projected/shared screen.
- For a saved-result tour, open the intended run and an already verified export.
  State which results remain Pending and whether the session permits review edits.
- For media, check play/pause/seek, the intended recording and transcript, and the
  label identifying the input used for grading. Explain transcript-based grading
  even when a source recording is visible.
- For a live segment, confirm the selected model is ready and the processing
  route/cost is understood. Have the manual exercise and saved results ready as
  fallbacks. Do not begin a new model task merely to make a presentation look live.

## A short first session

This is a suggested sequence, not a claim of a timed rehearsal:

1. Explain the loop: input → rubric → suggested evidence/score → human review →
   export. Use [the common vocabulary](audience-guide.md#words-used-in-the-demo).
2. Read the three fictional notes and score before revealing answers. Find the
   goal, barrier and next step; distinguish explicit evidence from assumptions.
3. Discuss disagreements. The original practice rubric is not a validated
   instrument and the authored examples are not a model benchmark.
4. If an application tour is prepared, name the actual package, model and graded
   input. Inspect one saved criterion and its source. Review edits, if agreed,
   belong on a designated synthetic practice record; refresh to confirm persistence.
5. Download a saved export and reopen it. Match sample/criterion rows, scores and
   review state. A browser toast alone is not delivery.
6. Give participants [Getting started](getting-started.md), their matching kit
   instructions and the [support route](support.md). Record any unfinished step.

Keep a rehearsed host available during new installs. Use the manual practice or
saved-result fallback if a live step fails. Preserve the failed state for support;
never substitute a private case packet or silently switch provider/processing route.

## Recipient handoff

Provide the exact kit/hash, prerequisites, daily commands, permitted sample,
model route if relevant, successful-run checklist and support contact. Credentials
stay in the recipient's locally generated helper. Verify their installation,
login, sample visibility and retained restart independently. Reopening an export
and checking its contents are separate from installing successfully.

Keep device journals privately. Public reports should contain generic synthetic
reproductions, not participant identities, host paths, screenshots of records or
full diagnostics. A workshop's saved-results tour is not recipient installation
acceptance, model calibration or clinical validation.

## Site pilot template

Use this for a later UT-REAL or other site pilot. It does not establish deployment,
institutional data-use approval or clinical validation. Fill it in the site's
appropriate private workspace.

```text
Pilot label:
Host/contact (private):
Demo objective and format: manual / saved results / agreed live segment
Approved demo ID and synthetic/public-domain input hashes:
Package revision/hash and operating system/architecture:
Model/provider, processing location and expected cost (if used):
Prerequisite / install / login / retained-restart results:
Actual graded input type and media/source-linkage checks:
Grading / human review / export / reopened-export results:
Which steps were not run:
Fallback demonstration:
Open problems and next owner:
Recipient instructions location:
Date and scope of acceptance:
```

Begin with public synthetic content. Institutional notes, proprietary rubrics,
private media and operational identifiers belong to a separately governed phase,
never this repository, its issues or public demonstration screenshots.
